## 2. "Which clock?" rule (`packages/api/src/clock.ts`)

In `packages/api`, not the engine (the engine stays calculation-only and unchanged) and not the web app (so it is tested with the endpoints, without a server). By the birth's local date, inclusive, India (`IN`) only:

| Window | Where | From | To | Options, default first |
|---|---|---|---|---|
| `india-before-1906` | anywhere in India | — | 1905-12-31 | IST +5:30 · LMT (longitude × 240 s, rounded) |
| `mumbai-1906-1955` | Mumbai (`isMumbaiPlace`) | 1906-01-01 | 1955-12-31 | IST · Bombay +4:51 |
| `west-bengal-1906-1948` | West Bengal (IN.28) | 1906-01-01 | 1948-12-31 | IST · Calcutta +5:53:20 |
| `war-1941-1942` | anywhere in India | 1941-10-01 | 1942-05-14 | IST · War Time +6:30 |
| `war-1942-1945` | anywhere in India | 1942-09-01 | 1945-10-14 | **War Time** · IST |

Overlaps (D-090): all options of every matching window (e.g. Mumbai 1943: War Time, IST, Bombay); default War Time only in 1942-09-01 – 1945-10-14. Outside the windows: the place's IANA zone. A clock choice that isn't offered → `INVALID_CLOCK_CHOICE`. 56 tests: every window, first and last day, the day after, overlaps, London/Karachi/Dhaka in the same years (no question).

## 5. CPU and the free plan

Hobby includes **4 hours of active CPU a month** (≈ 14,400 s; 1 million invocations).

| Request | CPU |
|---|---|
| Chart, warm | 2–5 ms |
| Chart, cold start | ≈ 20 ms + start-up |
| Search, warm | average ≈ 30 ms (0.4–106 ms) |
| Search, cold start (index load) | ≈ 1 s |

A visitor typing a place sends roughly one search per letter after the third (say 8), then one chart. Per visitor ≈ 8 × 30 ms + 5 ms ≈ 0.25 s.

- **100 visitors a day:** ≈ 25 s + ~20 cold starts (≈ 20 s) ≈ 45 s/day ≈ **23 min/month ≈ 10 % of the free CPU.**
- The free CPU runs out at about **1,000 visitors a day** (≈ 4 h/month). Search is the cost; charts are almost free.

**Abuse:** the endpoints are public. A script sending 3-letter searches non-stop could use up the month's CPU in a few hours (~10 per second). Free ways to limit it, not built:
1. **0.2.13 form:** wait ~250 ms after the last keystroke before searching (debounce), and cancel stale searches. Cuts normal use by more than half.
2. **Vercel Firewall** (in the dashboard, free on Hobby): a custom rule that blocks/challenges request bursts to `/api/*`, and "Attack Challenge Mode" for emergencies. Check what rate-limit rules Hobby allows before relying on them.
3. Vercel pauses the project when the free limit is reached; nothing is billed (no card on file).

## 7. To decide (Project) and small technical choices

**To decide**
1. **1 January 1800, early morning east of Greenwich.** The ephemeris data files start at about 01:08 UTC on 1800-01-01 (06:38 in India). Earlier instants get `DATE_OUT_OF_RANGE` now, although FR-IN-02 allows that date. Options: add the older Swiss Ephemeris files (`sepl_12.se1`/`semo_12.se1`, about 1.6 MB more, an engine change) or accept it.
2. **1906-01-01, 00:00–00:08:49 outside Mumbai/West Bengal.** The tz database moves India's clocks forward by 8 min 50 s that midnight, so those times "did not exist" → `NONEXISTENT_LOCAL_TIME`. Option: extend the pre-1906 window by one day, or accept.
3. **Pre-1906 default vs the tz database.** Before 1906 the default is IST (+5:30, D-082), while the tz database (and R22's true clock) uses Madras time +5:21:10. A Chennai 1901 birth entered with the default differs from R22 by 8 min 50 s; picking LMT gives +5:21:07 (Chennai's longitude). As D-082 decided; flagged only so the warning note in 0.2.13 is written knowing it.
4. Search results don't carry `matchedName` (e.g. "Bombay" matched Mumbai). The handoff's field list didn't include it; easy to add if the form wants to show it.

**Small technical choices**
- New package `packages/api` for the endpoint logic and clock rule; routes in `apps/web` are thin. The search route imports `@jathag/api/search-endpoint`, which never imports the engine (a test follows its imports). This was found on the first preview: importing the whole package crashed the search function, which deliberately has no Swiss Ephemeris binary.
- Request fields: `place` (search result fields) or `manual` (`lat`, `lng`, `utcOffsetSeconds`), `clock` (`ist`, `war`, `bombay`, `calcutta`, `lmt`), `repeatedTime` (`earlier`/`later`), `settings`. Clock options listed default first, then ist, war, bombay, calcutta, lmt.
- All input errors are HTTP 400 (413 for a body over the limit: 4 KB chart, 1 KB search; 100-character query). Unknown extra fields are ignored. An ambiguous time returns only the code, not the two possible instants (they'd echo birth data).
- Responses carry a `Server-Timing` header (times and CPU only) for measuring, and `X-Robots-Tag: noindex`.
- `maxDuration` 10 s (chart) / 15 s (search) caps runaway requests.
- Mumbai list copied into `clock.ts` (4 GeoNames ids) so the chart function doesn't need the index; a test keeps it equal to `data/places/mumbai-no-district.json` and the index.
- Bundling the engine: Turbopack rejects the engine's `new URL('../../ephe/', import.meta.url)` (a folder). Instead of changing the engine, a build-only loader (`apps/web/bundler/engine-ephe-path-loader.cjs`) replaces that one line in the bundle with a placeholder, and the chart route passes the real ephemeris path. The loader stops the build if the engine line ever changes. A later engine step could make this unnecessary.
- `sweph` added as a direct dependency of `apps/web` (same version, already installed; needed to keep it out of the bundle) and its Linux binaries copied into the chart function explicitly (sweph finds them at run time, so the tracer misses them).
