# 0.2.11 — GeoNames place index: feasibility report

*Claude Code, 2026-11-21. Step 0.2.11. For review in the Claude Project (D-075).*

## 1. Summary in plain English

1. **Built:** a place index of **788,038 places**, made from the free GeoNames data: every Indian populated place (**558,033**, villages included) plus every town of 500+ people worldwide (**230,005**). The build script, pinned sources, search package and 30 tests are in this PR.
2. **Search works and is fast:** every old name finds the modern city (Bombay → Mumbai, Madras → Chennai, Calcutta → Kolkata, Bangalore → Bengaluru, Trivandrum → Thiruvananthapuram, Poona → Pune). On Vercel, a search for a real name takes **under 1 ms**.
3. **The problem is loading:** on Vercel's free plan a server gets 1 CPU, and building the index in memory takes **5–9 s** on the first request after the server starts ("cold start"). That is too slow for type-ahead. A quick experiment showed that doing the heavy work at build time instead brings it down to **0.8 s**, using about 40% less memory. I recommend doing that in 0.2.12 (section 6).
4. **Where it should live:** inside the server function, with the index file committed to git (17 MB, well under the 50 MB rule; no Git LFS). Not in the browser: the download would be about 17 MB.
5. **Important finding for the "Which clock?" rule (D-082):** GeoNames gives **Mumbai itself no district**. Bandra and Andheri are tagged "Mumbai Suburban" and Colaba "Mumbai" (Mumbai City), but the main Mumbai entry, the one users will pick most, only has the state. A rule based on district alone would miss Mumbai. Options are in section 7.

| `packages/places/test/` | 30 tests (run by `pnpm test` and CI) |

The raw GeoNames downloads are **not** committed. Important: **GeoNames replaces its dump files daily and keeps no old copies**, so the checksums prove which data was used but cannot get it back. If exact rebuilds of *this* index matter, the five source files (32 MB) should be kept somewhere: a free GitHub Release attachment on the repo (not LFS) or the founder's own drive. Open question Q4.

**Deterministic:** rebuilding from the same five files gives a byte-identical `places.tsv` (I checked a full rebuild against the committed index). A test also builds a small made-up data set twice, once with the input rows in reverse order, and gets identical output.

## 4. Sizes, memory and timings

### Size

| | Size |
|---|---:|
| Index, unpacked (`places.tsv`) | 55.8 MB |
| gzip (committed) | **17.1 MB** |
| brotli (best) | 13.1 MB |
| of which alternate names (unpacked) | 3.9 MB |

### Measured on Vercel (preview of the throwaway branch `spike/0.2.11-places`, region iad1, Node v26.13.1, x64, **1 CPU**, Hobby defaults)

| Measure | Result |
|---|---|
| Cold start: read + unzip + build the in-memory index | **9.3 s**, 5.0 s, 5.4 s (three cold starts) |
| of which: read file 5–29 ms · unzip 0.3–0.5 s · build index 4.7–8.7 s | |
| Phases of the build on Vercel: split rows 1.6 s · normalise names 1.0 s · sort names 1.8 s | |
| Memory after loading (whole process) | 680 MB (heap 274 MB); 2 GB available |
| Search, real names (Bombay, Kumbakonam, Aurangabad, London …) | median **0.01–0.16 ms**, slowest 3.6 ms |
| Search, 2-letter queries ("ba", "ka", "ma" …): slow cases | median **9–137 ms**, slowest 485 ms |
| All 29 test queries × 25 runs | median 0.06 ms, 95th percentile 129 ms |
| **Prototype: names normalised and sorted at build time, rows read only when needed** | load **0.8 s**, memory 425 MB (heap 101 MB) |
| Fetching the same file from Vercel's CDN instead of the function bundle | +0.9 s download, then the same build cost (6.2 s total) |

For comparison, the same load takes 1.6 s on the Mac. Vercel's single CPU is about 3–5× slower.

**What this means:** after the first request, searches are instant. But Jathag will have few visitors at first, so many visits will hit a cold server. Waiting 5–9 s for the first suggestions is not acceptable. With the prototype approach the wait is under a second. Two-letter queries can take 100+ ms. The simple fixes are to start suggesting at 3 letters, or to precompute the top 10 for each 2-letter start (Q3).

**Fit:** the 17 MB index is far below the 250 MB bundle limit, and the measured 425–680 MB of memory is well below 2 GB. Each cold start at today's 5–9 s uses that much **active CPU** out of the 4 hours a month: about 1,600–2,900 cold starts. With the 0.8 s approach it would be about 18,000. This is another reason to do the optimisation.

## 5. Where should the index live?

| Option | Numbers | Verdict |
|---|---|---|
| **A. Inside the server function** (file traced into the bundle) | 17 MB of the 250 MB limit; read from disk in 5–29 ms | **Recommended** |
| B. Separate static file, fetched by the server | +0.9 s per cold start for the download; same build cost; adds a network dependency and needs care with preview protection | No benefit |
| C. Shipped to the browser | 17 MB gzip download (13 MB brotli) before the first suggestion: about 14 s on a 10 Mbit/s phone connection, and on a phone at least the 5 s build measured on Vercel's CPU, plus ~300–700 MB of memory. An India-only or towns-only browser version would leave out villages, against FR-IN-05 | **Confirmed too big** |

Option C would have one advantage: place searches would never reach our server, which is best for privacy (FR-API-02). With option A the API must make sure queries are never logged. Because it is our own code with no logging, that is easy to keep. It is worth a test in 0.2.12 that the place route does not log.

## 6. Recommendations

1. **Location:** option A, inside the server function, loaded once per server instance.
2. **Commit the generated index:** yes. `places.tsv.gz` is 17 MB (no file over 50 MB; no LFS). Vercel and CI get it without downloading from GeoNames, and every deploy uses exactly the reviewed data. Cost: each refresh of the GeoNames data adds about 17 MB to the git history. Refresh rarely, e.g. once before launch and then once or twice a year. Don't commit the 56 MB unpacked file (it would break the 50 MB rule).
3. **Feature codes:** include all of them (as built). Keep PPLX (city neighbourhoods) and PPLL. For abandoned, destroyed and historical places, see Q1.
4. **Technical follow-up for 0.2.12 (before the API goes live):** move the heavy loading work into the build (store the normalised, sorted search names in the index; read place rows only when shown). It was measured at 0.8 s instead of 5–9 s. The index format becomes version 2, about 7 MB larger gzip (~24 MB, still well under the limits). I did not do it in this PR, because the step is about measuring and the current version passes every test. It is a small, contained change in `packages/places`.
5. **Alternate names:** keep the current rule (section 8).

## 8. Alternate names: what is kept and why

Each GeoNames row lists all known names in all languages and scripts (Mumbai has 86). We keep a name only if it:
- is in **Latin script** (people type in English letters; Indian scripts would matter for v1.7 languages and can be added then);
- **starts with a capital letter** (this drops lower-case machine transliterations such as "bmbyy");
- is **not a 2–4 letter code** (airport codes such as BOM, MAA);
- has no " - " (Wikipedia-style pairs) and is at most 60 characters;
- is **not just another spelling** of a name already kept, after removing accents and case.

This keeps all six old names in the tests (and more, e.g. Chhatrapati Sambhajinagar → Aurangabad, Kudanthai → Kumbakonam). It costs 3.9 MB of 55.8 MB.

**Side effect:** GeoNames' Latin-script names include many foreign-language spellings (e.g. "Maeskuy" for Moscow, "Triva" for a small town in Louisiana). So an alternate-name match is ranked as if the place were 10 times smaller, and exact matches come first. "Bomb…" still finds Mumbai first, but a typed short name can bring an odd exact match to the top ("triva" shows Clayton, Louisiana before Thiruvananthapuram). If this is a problem, the more precise option is GeoNames' separate alternate-names file, which tags each name with its language and an "historic" flag: 1.4 MB for India, much more worldwide.

## 9. Disputed areas: how GeoNames labels them (report only)

GeoNames mostly follows **who administers the area today**, not India's official map (with one exception, Aksai Chin, below):

- **Pakistan-administered Kashmir and Gilgit-Baltistan** are listed under **Pakistan**: Muzaffarabad → "Azad Kashmir, Pakistan" (PK.06), Gilgit and Skardu → "Gilgit-Baltistan, Pakistan" (PK.07), time zone Asia/Karachi. India's official position is that these are part of India (Jammu and Kashmir / Ladakh).
- **Indian-administered Jammu and Kashmir** (IN.12, 11,565 places) and **Ladakh** (IN.41, 481 places, e.g. Leh, Kargil) are under India, Asia/Kolkata.
- **Arunachal Pradesh** (IN.30, 451 places, e.g. Itanagar) is under India.
- **Aksai Chin** (administered by China, claimed by India) is almost empty in the data. In a rough box around it I found only 2 populated places, both listed under **India** (Ladakh, Leh district, Asia/Kolkata): Sumdo (1255470) and "K'o-shih-erh-ts'un" (1266074, a Chinese-style name). So GeoNames is not fully consistent: here it follows India's claim, not who administers the area.
- **Odd case:** 3 villages listed under India (Jammu and Kashmir, Punch district) have the Pakistan time zone **Asia/Karachi**: Abbaspur (12524521), Pumnuthi (13060542) and Fārward Kahūta (13527012). Their coordinates appear to be on the Pakistan-administered side of the Line of Control. A test records them, so any change in the data is noticed.

Why it matters: (1) **labels.** An Indian user typing Muzaffarabad will see "…, Pakistan". Indian law and practice on maps is strict, and some users may find this offensive. Others may expect it. (2) **Time zones for old births.** Places on the Pakistan side get Asia/Karachi. Before 1951 that zone gives the same +5:30 as India, but it differs afterwards, and D-082's India-only "Which clock?" windows would not apply there (this connects to O-007). Options for the Project (Q6): keep GeoNames' labels as they are (neutral, what most sites do); relabel these regions for Indian display; or show both, e.g. "Muzaffarabad, Azad Kashmir (Pakistan-administered Kashmir)". I changed nothing.

## 12. Small technical choices I made

- New workspace package `packages/places` (`@jathag/places`), same setup as the engine (TypeScript 5.9.3, `@types/node` 24.19.2, versions already in the repo; nothing new downloaded). `pnpm typecheck` now covers it.
- Index format: one gzipped tab-separated text file with small look-up tables for zones, countries, states and districts (no JSON, which is bigger). Population 0 is stored as empty.
- Zip files are read with Node's built-in zlib (no unzip tool or package needed).
- Search: prefix match on whole names, not on later words ("delhi" does not match "New Delhi" by its name, though "New Delhi" is also an alternate name of Delhi). Text after a comma narrows the results.
- The spike needed `allowImportingTsExtensions` in the web app's TypeScript settings to import the package. The same will be needed when the web app imports the engine or places in 0.2.12. (The spike branch is deleted, so this is not in this PR.)
- Throwaway branch `spike/0.2.11-places`: preview measured, branch deleted from GitHub and the Mac; nothing from it merged.
