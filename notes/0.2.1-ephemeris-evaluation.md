# 0.2.1 / 0.2.2 — Swiss Ephemeris for JavaScript/TypeScript: evaluation report

*Date: 2026-11-20 · Author: Claude Code · Status: report only. The choice is made in step 0.2.3 (Claude Project + Adithya).*

Legend: **✔ verified** = I checked it myself (ran code, read package files, or queried npm/GitHub on 2026-11-20). **? unsure** = taken from a README or my own reasoning, not tested.

---

## Summary for Adithya (plain English)

1. There are about 15 ways to use Swiss Ephemeris from JavaScript. Two stand out: **`sweph`** (the oldest and most used; it runs as compiled code on the server) and **`swisseph-wasm`** (a WebAssembly version that could also run inside a phone app later).
2. I tested both on our Vercel server. Both worked and gave **the same answers to within 0.004 arcseconds**, about 15,000 times tighter than our ±1 arcminute rule. The sanity checks passed: Sun 280.37°, Lahiri 23.85°.
3. Both are fast. On the server one full chart takes about a quarter of a millisecond, and starting up takes 26 ms (`sweph`) or 79 ms (WebAssembly). The data files for 1800–2400 are only 1.8 MB.
4. **My recommendation:** use **`sweph` on the server now**, hidden behind a small "adapter" in our engine. Then the phone app (v1.3) can plug in the WebAssembly version without changing any results.
5. Nothing costs money. All the options are AGPL-compatible, and you don't need to do anything except choose (step 0.2.3).

## 3. Spike test results (throwaway branch `spike/0.2.1-ephemeris`, now deleted)

The test time was 2000-01-01 12:00 UT (JD 2451545.0), with Chennai at 13.0827 N, 80.2707 E. The settings were the Swiss Ephemeris files, Lahiri, and whole-sign houses for the ascendant. The data files were Astrodienst's official `sepl_18.se1` and `semo_18.se1` (GitHub `aloistr/swisseph`) for `sweph`, and the copies bundled inside `swisseph-wasm`.

- **Agreement within 1 arcsecond: yes, for every value.** The largest gap is 0.004″.
- **Where the tiny gaps come from (✔ verified):** they come from **the data files, not the bindings.** When I pointed `sweph` at the older `.se1` copies that ship inside other npm packages, it reproduced the WASM numbers exactly. Astrodienst has re-issued these files over time.
  - Lesson: **pin the exact data files (with checksums) in the repo.**
  - The effect (≤0.004″) is negligible against our ±1′ rule (D-013).
- Sanity checks: Sun ≈ 280.37° ✔, Lahiri ≈ 23.85° ✔. Saturn and the nodes are correctly flagged retrograde (negative speed).
- For comparison, the built-in Moshier model (no data files) differs from the full files by only 0.09″ for the Moon on this date.

### 3.2 Speed and size

| Measure | `sweph` | `swisseph-wasm` | Where |
|---|---|---|---|
| Install time (`pnpm add`, warm cache) | 5.9 s | 1.1 s | Mac ✔ |
| Cold start: process start → first chart | 6–9 ms | 11–15 ms | Mac, 5 runs each ✔ |
| Cold start: load + first chart (first request on a fresh instance) | **26 ms** | **79 ms** | Vercel preview ✔ |
| 1,000 charts (9 bodies + ayanamsa + ascendant each, random dates 1800–2100) | 50 ms (Mac) · **219 ms** (Vercel) | 49 ms (Mac) · **345 ms** (Vercel) | ✔ |
| Memory growth after 20,000 charts | +0.1 MB | +0.4 MB (no leak seen) | Mac ✔ |
| Files traced into the function (both bindings + data + Next.js server files) | about **8 MB** in total | | local `next build` trace ✔. Vercel's limit is 250 MB uncompressed, so there is lots of room. I could not read the exact size on Vercel (it needs sign-in). |
| Vercel build | ✔ succeeded (after the fix below) | ✔ succeeded | ✔ |

- **Build gotcha found (✔ verified):** pnpm 12 refuses to install in CI or on Vercel when a package has an unapproved install script (`ERR_PNPM_IGNORED_BUILDS`), and `sweph` has one.
  - The script only re-checks the binary and runs `sweph`'s own tests. The prebuilt binary is found at runtime without it.
  - Fix: add `sweph: false` under `allowBuilds` in `pnpm-workspace.yaml`, as we already do for `sharp`. With that, CI and Vercel both passed.
- **Next.js setup needed (✔ verified):** list the binding in `serverExternalPackages` and add the data files to `outputFileTracingIncludes`. Otherwise they aren't copied into the function.

## 4. Risks and known problems

1. **Shared global settings (✔ verified, applies to both).** The C library keeps settings such as the sidereal mode and the data path process-wide.
   - What I saw: setting Raman in one "request" changed the next Moon result from 199.47° to 200.92°.
   - Why it's manageable: on Vercel each function instance handles one request at a time, and our calculations are synchronous.
   - Rule for step 0.2.8: set the ayanamsa immediately before each chart's calculations, and never `await` in between.
   - The `sweph` README also says worker threads share these settings. WASM avoids this: each instance has its own memory (✔ tested).
2. **Single maintainers.** Every candidate is essentially run by one person.
   - `sweph`: 5 years of history, about 30k downloads/week, and it wraps the newest Swiss Ephemeris (2.10.03).
   - `swisseph-wasm`: at version 0.1.0 and about a year old.
   - Mitigation: wrap whichever we pick behind our own small adapter in `packages/engine`, and let the reference tests catch any regression. Swapping bindings then becomes a one-file change.
3. **Silent fallback (⚠ `swisseph-wasm`).** If the data files fail to load, Swiss Ephemeris quietly uses the Moshier model. `sweph` tells us when this happens; the `swisseph-wasm` wrapper doesn't. The difference would be small (~0.1″), but we'd want to know.
4. **Native binary on Vercel.** It depends on Vercel staying on Linux x64 or arm64 (prebuilds exist for both). N-API binaries keep working across Node versions (✔ it ran on Node 26).
5. **Data-file versions.** Covered in §3.1: pin the files and their checksums.
6. **Phone app.** No candidate is proven inside React Native. WASM inside Capacitor is very likely fine but untested (? unsure). This matters only from v1.3, and the mobile framework itself is still open (D-045).
7. **No network at runtime.** `sweph-wasm` and `@swisseph/browser` fetch data files from a CDN by default. That would be an extra outside dependency and, from the browser, a privacy leak. I'd avoid both for the server.

## 5. Recommendation (the decision is made in 0.2.3)

**Use `sweph` for the server engine now. Put it behind a thin adapter interface in `packages/engine`, and keep `swisseph-wasm` (or another WASM build) as the planned route for the offline phone engine (v1.3).**

Reasons:
- `sweph` is the most mature and most used option, and it wraps the newest Swiss Ephemeris version.
- It has the most complete TypeScript types.
- It reports errors and which ephemeris was actually used on every call.
- It is the faster of the two on Vercel.
- Its licence (AGPL/LGPL) is the cleanest fit.
- Both bindings produced the same numbers, so choosing one now doesn't lock the phone app out later. The adapter plus the JHora reference tests (0.2.7) will prove any later swap gives identical results.

Alternative if the Project prefers one binding everywhere from day one: use `swisseph-wasm` on the server too. It works on Vercel and is fast enough. The costs are a younger, smaller project, no error flags without our own patch, and a slightly slower cold start (79 ms against 26 ms).
