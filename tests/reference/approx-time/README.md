# Approximate-time test cases (step 0.3.5)

Expected output for the approximate-time scanner (step 0.3.6). Written by the Project (decisions D-107, D-109); `cases.json` is data only. Nothing here is a real person's birth: every case reuses a synthetic reference birth from `../births.json`, with a made-up time range.

## The five cases

| Case | Reference birth | Time input | What it covers |
|---|---|---|---|
| A1 | R01, Chennai, 1992-08-14 | range 06:00–12:00 ("Morning") | three Lagna signs, a Moon nakshatra change (dasha lord Mars → Rahu), Moon sign certain |
| A2 | R13, Kolkata, 1970-02-05 | range 06:00–06:30 | Lagna sign, Moon and dasha lord all certain; only Lagna nakshatra/pada change; dasha dates still move by ~7 weeks |
| A3 | R04, Kolkata, 1978-03-21 | range 18:00–20:00 | Moon sign and nakshatra change together (Mercury → Ketu), a Lagna sign change |
| A4 | R07, Chennai, 1936-10-02 | whole day ("don't know") | all 12 Lagna signs, a Moon sign change, three dasha lords; speed target under 5 s on production (FR-API-03) |
| A5 | R16 place (Newark, New Jersey), 2001-10-27 20:00 EDT → 2001-10-28 06:00 EST | range across midnight and the clock going back | 11 real hours; local 01:00–02:00 happens twice ("first" / "second") |

A range includes both of its end moments.

## `cases.json`

- `toleranceSeconds` (2): the scanner's change moments must be within this of `events[].utc`.
- `values`: the six values tracked. `ls` Lagna sign, `ln` Lagna nakshatra, `ld9` Lagna sign in the navamsa (changes at every Lagna pada boundary), `ms` Moon sign, `mn` Moon nakshatra (the dasha lord changes with it), `mp` Moon pada. Signs 1–12 from Aries, nakshatras 1–27 from Ashwini.
- per case:
  - `fromUtc`/`toUtc`, `fromLocal`/`toLocal` (birth-place clock); `clockOffsetSec`, or `clock` (A5: the change at 06:00Z).
  - `atStart`/`atEnd`: the six values at both ends.
  - `certain`: values that never change inside the range (the rest are uncertain).
  - `events`: every moment something changes, in time order, grouped by instant (several values can change at once). `utc` is the first whole second of the new value; `local` the birth-place clock; `repeatedLocalTime` "first"/"second" inside A5's repeated hour.
  - `segments`: the maximal stretches in which all six values are constant (what the scanner returns, D-107 item 2), each with `from`, `to` (the last second before the next change; the last segment ends at `toUtc`) and its six values.
  - `dasha`: one entry per stretch with the same Moon nakshatra (= same dasha lord). Per entry the 9 mahadashas and 81 antardashas, each with the earliest and latest start and end (`startMin`, `startMax`, `endMin`, `endMax`), taken from the Vimshottari timeline at the first and last second of the stretch (dates move steadily, so the two ends give the extremes; D-107 item 4). Dates are exact UTC.
  - `jhoraChecked`: moments the founder compared in JHora (before/after, whole minutes): all matched (D-109).

## How the data was made

For each case the engine (0.4.0, Swiss Ephemeris, Lahiri, whole-sign) computed the six values every minute over the range, and every change was narrowed to the whole second by bisection. This is deliberately a simple brute-force method, independent of the 0.3.6 scanner. Four moments (A1 Lagna and Moon, A3, A4) were confirmed in JHora with the D-103 settings. A2 has no JHora reading (same method as the others); A5's clock change is checked by arithmetic (UTC offset −4 h until 06:00Z, −5 h after).

If the engine changes in a way that moves a result, these files must be regenerated by the Project and re-checked, not edited by hand.
